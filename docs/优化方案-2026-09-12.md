## 一、总体评价

### 1.1 架构健康度

分层清晰，职责边界合理，对求职项目而言结构合格：

| 层 | 组织方式 | 评价 |
|---|---|---|
| 前端渲染层 | `utils/cesium.js` 纯函数封装 | ✅ 无状态、可复用，949 行但职责单一 |
| 前端编排层 | `CesiumViewer.vue` + `window` 自定义事件总线 | ⚠️ 事件总线无类型约束，事件名散落在 3 个文件里，改名即静默失效 |
| 前端状态层 | `stores/map.js` 单一 Pinia store | ✅ 集中，但把 viewer 实例放进响应式 store 属于反模式（Cesium 对象被 Proxy 包裹，深度监听有性能开销） |
| 后端业务层 | Controller → Service → Mapper | ✅ 标准，`@Transactional` 边界正确 |
| 后端调度层 | 4 个独立 `@Scheduled` | ⚠️ 无显式线程池配置，依赖 Spring 默认单线程调度器；彼此通过 DB 交互而非内存共享，正确但脆弱 |
| 数据层 | PostGIS + pgRouting 导航网格 | ✅ 设计思路（15m 栅格 + 边级过滤 + 成本惩罚）合理且是项目最大亮点 |

### 1.2 亮点（应保留并在面试中重点讲）

1. **边级限飞区过滤**（`05_setup_pgrouting_navigation.sql:173-179`）：用 `ST_DWithin(nfz.geom::geography, v_edge_geom::geography, 5.0)` 过滤跨区边，解决了"两端点都在区外但连线穿区"被网格粒度漏掉的经典问题 —— 这一点做得比多数同类项目扎实。
2. **成本惩罚软约束**（同文件 `:195-197`）：靠近限飞区的边按距离线性加价，避免 A\* 贴边飞行。
3. **真实穿越检测双口径**（`RouteServiceImpl.java:101-122`）：同时检测"起终点直线"与"规划路径边集"，返回三态结果给前端 —— 可验证性强。
4. **派单双行锁**（`OrderServiceImpl.java:106` + `DroneMapper.java:16,23`）：订单行 + 无人机行均 `FOR UPDATE`，锁持有至事务提交，并发派单问题解决得干净。
5. **距离口径已统一到 geography**：`NavigationMapper.buildRouteFromNodes` 用 `ST_Length(...::geography)`，与 `DroneServiceImpl.haversine` 推进同口径，`estimated_seconds` 因此可信。

>

### P0-2　MVT 矢量瓦片接口从未成功返回过数据（每次请求都抛异常，且被吞掉）　✅ **已修复并验证**

| 项 | 内容 |
|---|---|
| 位置 | `backend/src/main/resources/mapper/TileMapper.xml:14` 与 `backend/src/main/java/com/campus/twin/mapper/TileMapper.java:22-25` |
| 代码（修复前） | XML：`<select id="selectMvt" resultType="byte[]">`；接口：`byte[] selectMvt(@Param("table") String table, @Param("z") Integer z, @Param("x") Integer x, @Param("y") Integer y);` |
| 根因 | 两处叠加：<br>① **别名解析**：MyBatis `TypeAliasRegistry` 把 `byte[]` 注册为 **`java.lang.Byte[]`（对象数组）**，原始类型数组的别名是 `_byte[]`（已在 `mybatis-3.5.15-sources.jar` 的 `TypeAliasRegistry.java:45/56/67/78` 逐行核对：`"byte"→Byte.class`、`"byte[]"→Byte[].class`、`"_byte"→byte.class`、`"_byte[]"→byte[].class`）。于是每行被映射为 `Byte[]` 而非 `byte[]`。<br>② **返回类型判定**：`MethodSignature.returnsMany = ... \|\| this.returnType.isArray()`（`MapperMethod.java:294`），而 `byte[].class.isArray()` 为 **true** → 方法被当作"返回多行"处理，走 `executeForMany` → `convertToArray`。`convertToArray`（`MapperMethod.java:179-189`）取 `getComponentType()` 得到基本类型 `byte`，进入 `Array.set(array, i, list.get(i))` 分支 —— 这一步对 `Byte[]` 元素必然抛 `IllegalArgumentException: argument type mismatch` |
| 实测到的异常 | 用真实 mapper + 真实库实测，异常**发生在类型处理器读取阶段**（早于 `Array.set`）：<br>`org.apache.ibatis.executor.result.ResultMapException: Error attempting to get column 'mvt' from result set.`<br>`  Cause: org.postgresql.util.PSQLException: 不能转换类型 byte : \x`<br>即两条失败路径（处理器读取 / `Array.set`）**任选其一都会失败**。结果是每行元素变成 `[Ljava.lang.Byte;`，方法无法返回可用的 `byte[]` |
| 后果 | `TileServiceImpl` 用 `catch (Exception e) { log.warn(...); return new byte[0]; }` 吞掉异常 → `TileController` 对**任意 table/z/x/y** 返回 **HTTP 200 + Content-Length: 0 + `Cache-Control: max-age=3600`**。即一个"永远成功、永远空、还被浏览器/CDN 缓存 1 小时"的假接口。MVT 是 README"面试亮点"第 6 条，实际从未产出过数据 |
| 修复 | 改为"多行 + 取首行"，**必须同时改 XML 别名**（只改返回类型或只改别名都不行）：<br>① `TileMapper.java`：`List<byte[]> selectMvt(...)`（并加注释说明别名陷阱）<br>② `TileMapper.xml`：`resultType="_byte[]"`（**下划线前缀 = 基本类型数组**）<br>③ `TileServiceImpl.java`：`List<byte[]> rows = tileMapper.selectMvt(...); return rows == null \|\| rows.isEmpty() ? new byte[0] : rows.get(0);`<br>④ `catch` 里的 `log.warn` 升级为 `log.error` 并保留堆栈，避免再次静默空响应 |
| 验证（已执行） | ① **编译**：`mvn -o compile`（JAVA_HOME=JBR 25）通过。<br>② **真实 mapper + 真实库**：用 `backend/target/classes` 下真实的 `TileMapper.class` 与 `TileMapper.xml` 装配 MyBatis 3.5.15 直连 `shp_data`，同一瓦片 z=15(26803,12641)：<br>　· 修复前 XML（`resultType="byte[]"`）→ `school`/`teaching_building`/`dormitory`/`road` **全部** 返回 `[Ljava.lang.Byte;`（类型错误）<br>　· 修复后 XML（`_byte[]`）→ 分别返回 `byte[77]` / `byte[431]` / `byte[573]` / `byte[860]`<br>③ **真实 HTTP 端到端**：在 8081 端口另起一个临时实例（未触碰你的 8080），同一 z=15 瓦片实测：<br>　· **8080（旧实例，未修复）：8 个图层全部 `bytes=0`**<br>　· **8081（新编译）：`school=77B`、`teaching_building=431B`、`dormitory=573B`、`other_buildings=462B`、`road=860B`、`playground=118B`、`basketball_court=80B`、`tennis_court=76B`**<br>④ **protobuf 结构校验**：`dormitory` 瓦片首字段 `1A BA 04` → 解码出图层名 `dormitory`，MVT 结构合法 |
| 说明 | 此缺陷属于"接口实现坏了"，与 `bugfix-plan-2026-09-11.md` 的 **M13（MVT 接入 Cesium / 缓冲区查询 UI 闭环，未实施）** 是两件事。本次只修接口正确性（改动 < 10 行）；前端是否接入 MVT 仍按 M13 单独立项 |
| ⚠️ 排查提示 | 定位瓦片时**不要靠猜 z/x/y**。本项目 8 个图层的实际范围（均为 SRID 4326）为 lng 114.4629–114.4727、lat 37.9815–37.9871，对应 **z=15 → (26803,12641)**、**z=16 → (53606,25282)**。一开始我猜的 z=18 (216073,99810) 是校园西侧之外的瓦片，导致"修复后仍为 0 字节"的假象并浪费了一轮排查 |

### P1-1　缓冲区查询半径单位错误（米 → 度）
| 项 | 内容 |
|---|---|
| 位置 | `backend/src/main/resources/mapper/SpatialQueryMapper.xml:49-53` |
| 代码 | `WHERE ST_DWithin(ST_SetSRID(geom,4326), ST_SetSRID(ST_MakePoint(#{lng},#{lat}),4326), #{radius})` |
| 根因 | `geom` 是 `geometry(4326)`，`ST_DWithin(geometry, geometry, double)` 的第三参按**坐标单位（度）**解释。而 JavaDoc（`SpatialQueryMapper.java:34`）与前端（`frontend/src/api/spatial.js:11`）都把 `radius` 定义为**米** |
| 后果 | 传 `radius=100` → 实际范围约 **100 度**。虽然在校园经度范围外会退化，但语义完全错误；传 `radius=1000` 即覆盖半个中国 |
| 现状 | 目前是**潜伏缺陷**：`BuildingPopup.vue:172-174` 的"周边查询"只弹 `ElMessage.info` 占位，接口无前端调用方。一旦接线立即暴露 |
| 修复 | 与同文件 `selectByBuffer` 的距离计算保持一致，改用 geography：<br>`WHERE ST_DWithin(ST_SetSRID(geom,4326)::geography, ST_SetSRID(ST_MakePoint(#{lng},#{lat}),4326)::geography, #{radius})` |
| 附带 | `ORDER BY distance_m` 用的是 geography 距离别名，保持不变即可。建议同时给 `radius` 加 `@Param` 校验（>0 且 < 5000） |

### P1-2　食堂覆盖"圆"与"实际覆盖列表"口径不一致

| 项 | 内容 |
|---|---|
| 位置 | 后端 `RestaurantServiceImpl.java:137-148`；前端 `utils/cesium.js:882-919`、`CanteenCoverageQuery.vue:56-63` |
| 根因 | **分档依据**是 A\* 实走距离：`DormitoryCoverageVO.seconds = ceil(routeDistanceM / 5.0)`（`:127`），其中 `routeDistanceM` 沿 15m 栅格 8 邻域路径累计，**必然 ≥ 直线距离**。<br>**而画的圆**半径是 `sec * FLIGHT_SPEED`（`:143`），即 30/60/90s → 150/300/450m 的**直线半径**。<br>前端图例（`CanteenCoverageQuery.vue:56-63`）明确写"30s · 150m"，3D 圆也用 `tier.radius` 画椭圆（`utils/cesium.js:896-908`） |
| 后果 | 绕行限飞区时 A\* 路径显著长于直线，**圆内不含该宿舍，但面板列表里却有它**（或反之）。用户点"30s 档"看到列表 N 栋、地图圈里 M 栋，N ≠ M。这是演示时最容易被追问穿帮的点 |
| 影响 | 食堂覆盖是项目的独立亮点功能（`docs/superpowers/specs/2026-09-10-canteen-coverage-design.md`），口径不自洽会直接削掉这个亮点 |

**推荐修复（保留"路径时间"这一更有技术含量的口径）**

1. **后端**：不再下发 `radius`，改为下发**该档覆盖宿舍的凸包/缓冲区多边形**（`ST_ConcaveHull` 或 `ST_Buffer` 沿路径），或至少下发每个 `DormitoryCoverageVO` 的**路径折线**。
   - 轻量版：`TierCoverageVO` 增加 `reachPolygon`（GeoJSON 字符串），由 `ST_Union(ST_Buffer(路径线::geography, 30))` 生成 —— 语义变成"可达区域"，与列表严格自洽。
2. **前端**：`loadCanteenBuffer` 改为渲染 `reachPolygon` 面而非椭圆；`CanteenCoverageQuery.vue` 图例文案从"30s · 150m"改为"30s 可达区（沿导航路径）"。
3. **兜底版（若不想动几何生成）**：保留椭圆，但把半径改为"该档覆盖宿舍的**最远实走距离**"，并把文案改为"30s 导航可达范围"，同时明确圈是**示意**而非边界。

> 三个版本工作量递增，但都必须消除"圈是否包含某宿舍"这个可被直接校验的不一致。

```powershell
$env:JAVA_HOME = "C:\jdk-17.0.20+8"
mvn -f backend/pom.xml test
```

> 注意：**编译**用 JDK 25 也能过，但**跑测试**必须 JDK 17。
