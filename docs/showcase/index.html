01空间数据：自己生产，不是下载的

项目的空间底料不是现成数据集。8 个校园图层、共 62 个要素， 全部是在 ArcMap 中依影像底图手工矢量化完成：绘制几何、录入属性 （建筑名称、层高、所属院系、宿舍性别）、做拓扑与几何检查，再导出 Shapefile 导入 PostGIS。

影像底图→ ArcMap 矢量化 + 属性录入→ 拓扑与几何检查→ Shapefile→ PostGIS 入库 + GiST 索引→ Cesium 渲染

为什么这条重要：WebGIS 岗位的候选人里，会写地图组件的人很多， 但能自己完成「影像 → 矢量数据 → 属性建库 → 规范化入库」的人很少。 这条链路决定了数据来源、坐标系、精度这些底层问题的答案。

02坐标系：把一次错误判断查清楚

入库时统一标注 SRID 4326（WGS84）。经实测核查， 14 个空间列的 SRID 完全一致、无混用： 

-- 验证 1：声明 SRID 是否统一（geometry_columns 是 PostGIS 元数据视图）
SELECT COUNT(*) AS spatial_columns,
       COUNT(DISTINCT srid) AS distinct_srid,
       string_agg(DISTINCT srid::text, ',') AS srids
FROM geometry_columns;
 spatial_columns | distinct_srid | srids
-----------------+---------------+-------
              14 |             1 | 4326

-- 验证 2：数据是否为真经纬度 + 校园真实尺度
SELECT round(ST_Distance(
         ST_SetSRID(ST_MakePoint(ST_XMin(g),(ST_YMin(g)+ST_YMax(g))/2),4326)::geography,
         ST_SetSRID(ST_MakePoint(ST_XMax(g),(ST_YMin(g)+ST_YMax(g))/2),4326)::geography
       )::numeric,1) AS east_west_m,
       round(ST_Distance(
         ST_SetSRID(ST_MakePoint((ST_XMin(g)+ST_XMax(g))/2,ST_YMin(g)),4326)::geography,
         ST_SetSRID(ST_MakePoint((ST_XMin(g)+ST_XMax(g))/2,ST_YMax(g)),4326)::geography
       )::numeric,1) AS north_south_m,
       round(ST_Area(ST_SetSRID(g,4326)::geography)::numeric,1) AS area_sqm
FROM (SELECT ST_Union(geom) AS g FROM school) s;
 east_west_m | north_south_m | area_sqm
-------------+---------------+-----------
       834.7 |         626.5 |   328900.5

校园 834.7 m × 626.5 m，边界 17 个顶点。 数据确为经纬度——若是投影坐标，数值会是六位数（约 500000 / 4000000）。

踩坑：.prj 标注与实际不符

Shapefile 的 .prj 文件写着 GCS_WGS_1984， 但数据实际是按高德 GCJ-02（国测局加密坐标）基准采集的。 国内数据「标注 WGS84、实为 GCJ-02」是常见情况。 

GCJ-02 与 WGS84 在本校园处的合成偏移（Java 与 PostGIS 双向复算一致）
  北向偏移 = -56.8 m
  东向偏移 = -92.6 m
  合成偏移 = 108.6 m
我犯过的错误：最初我判断「数据是 WGS84、高德底图是 GCJ-02，所以底图偏了」， 于是把底图换成天地图（WGS84）。结果立刻出现约 108.6 米的偏移—— 这个偏移是我换底图造成的，不是数据的问题。 真实根因是数据与高德底图本来就同属 GCJ-02、零偏移。 最终方案：保留高德底图、不做任何平移，前端坐标平移量恒为 0。

这件事的教训：.prj 文件不可全信；且「图层之间彼此吻合」只能证明图层间一致， 不能证明整体坐标系正确——因为所有图层被同样平移后，彼此仍然吻合。

03A* 路径规划：把「禁飞」真正落进图里

这是项目的技术核心。要在校园里给无人机规划出既短又安全的航线， 需要把连续空间离散成可寻路的图结构，再把「不能飞」这一约束落到图里。

第一步：构建导航网格

  • 以校园边界外扩 50m 为范围，按 15m 分辨率生成网格中心点作为导航节点；
  • 节点若落在限飞区内（含 5m 安全缓冲）则标记为不可飞行；
  • 每个可飞行节点与周围 8 邻域的可飞行节点连边，边代价取两点间实际距离（米）。

实测规模：3,100 个节点、10,693 条边。 导航网格由脚本幂等重建，秒级完成，便于调整限飞区后快速刷新。

第二步：限飞区三级避让

层级做法解决的问题
节点级 节点带 5m 安全缓冲判定，落入缓冲区内即不可飞 保证起终点与途经点本身不在禁飞范围
边级过滤 源-目标线段穿越限飞区（含缓冲）则不建这条边 网格粒度会漏掉「两端点都在区外、但连线穿过限飞区」的情况
成本惩罚 距限飞区 15m 内的边，按距离比例抬高 cost（软约束） 防止航线贴着限飞区边缘飞行，留出安全余量
设计取舍：把避让拆成「硬过滤 + 软惩罚」两级，是因为 纯硬过滤会让航线紧贴限飞区边界（数学上最短路径总是贴着障碍边缘走）， 纯惩罚则无法排除真正穿越禁飞的边。 两者结合后，航线既能绕开禁飞区，又能自然走在安全走廊中间。

第三步：求解与校验

-- 用 pgRouting 在边表上求最短路径；起终点映射到最近的可飞行节点
SELECT * FROM pgr_astar(
  'SELECT id, source, target, cost, reverse_cost FROM drone_nav_edge',
  :start_node, :end_node, directed := false
);

-- 穿越检测：验证规划结果是否真的绕开了限飞区
SELECT fr.id AS route_id, nfz.name AS crossed_zone
FROM flight_route fr
JOIN no_fly_zone nfz ON ST_Intersects(fr.route_geom, nfz.geom);

另提供穿越检测接口：对起终点直线与规划路径分别做 ST_Intersects 判断， 返回穿越的限飞区明细——既验证算法效果，也让「为什么绕行」对用户可见。

04量算精度：从 5.6% 偏差到 <0.01%

测距用 Cesium 的球面距离（EllipsoidGeodesic.surfaceDistance）， 测面积用 ENU 局部切平面投影 + 鞋带公式。 这个组合不是随手选的，而是踩过坑之后定的。

曾经的错误实现：用 eastNorthUpToFixedFrame 返回矩阵的 列向量做点积来取局部坐标。
实测症状：100 米的边量出来是 72 米和 138 米， 面积偏差 5.6%。
注意 72 和 138 这两个数——一条边算短了、另一条算长了， 正是「非正交基投影导致剪切变形」的典型症状。

根因：那些列是位置矢量（模长≈地球半径 6371km），且 east/north/up 三列并非正交， 用非正交基做投影等于把正方形斜着压成平行四边形。
修正：改用 Matrix4.inverse 把世界坐标变到局部 ENU 系， 得到严格正交的（东、北）坐标，再套鞋带公式。 实测偏差降至 <0.01%。

取舍说明：距离用球面（有现成精确 API，成本低），面积用局部平面 （校园约 1 平方公里内 ENU 近似误差远小于用户关心的精度）。 为了那 <0.01% 去引入球面多边形面积算法，是过度工程。

05空间数据服务：索引与瓦片

能力实现方式
点选查询ST_Intersects 判断点与图层几何的空间关系
缓冲区查询ST_DWithin 以米为单位筛选（::geography，避免「度」当「米」用）
GeoJSON 输出按图层动态生成，前端 Cesium 直接加载
MVT 矢量瓦片ST_AsMVT + ST_AsMVTGeom 生成 protobuf 瓦片，按 z/x/y 提供
概览统计建筑总数/面积/平均楼层、道路条数与总长、运动场地数量

两个工程细节

① 动态表名的安全处理。 图层接口的表名来自前端，属动态 SQL。项目用白名单校验，只允许预定义的 8 张空间表通过，并针对性写了单元测试，从根上规避 SQL 注入。

② MVT 的索引命中取舍。 瓦片包络在 3857 下计算，但几何列是 4326、GiST 索引也建在原始列上。 若直接拿 3857 的包络去比 4326 的列，PostgreSQL 会隐式转换或干脆不用索引。 因此先用 ST_Transform(bounds, 4326) 转回 4326 走 && 预过滤命中索引， 再在子查询里做精确 ST_Intersects。

问题根因防护手段
Cesium 对象进 Vue 响应式 几何构建走 Web Worker，postMessage 含 Vue 的 reactive Proxy 时结构化克隆直接抛 DataCloneError 持有 Cesium 实例的状态统一用 shallowRef / shallowReactive，并写脚本校验
Cesium API 跨版本改名 wgs84ToWindowCoordinates 在新版本改名 worldToWindowCoordinates，旧写法语法合法、只在运行时抛 TypeError 封装兼容函数（新名 → 旧名 → null），并校验调用点
把布尔属性当方法调用 isLoading?.() 中 ?. 只对 null/undefined 短路；又因回调是 async，异常静默变成未处理的 rejection 点击处理器整体加 try/catch，脚本校验属性用法
测面积口径错误 变换矩阵列向量点积导致剪切变形（100m 边算成 72m / 138m，偏差 5.6%） 改用 ENU 逆矩阵变换到局部平面（实测偏差 <0.01%）

其他工程约束

  • 配置分环境：本地 profile 零配置可启动；生产 profile 强制由环境变量提供数据库连接，启动阶段即校验连通性（fail-fast），避免「启动成功但接口全 500」。
  • 破坏性操作默认关闭：历史脏数据清理会改写业务数据，因此默认不执行，需显式开启。
  • 服务分层：Controller 只做参数校验与响应包装，空间 SQL 集中在 Mapper 层，业务规则在 Service 层——便于单元测试覆盖，也让后续替换数据源时改动面可控。
